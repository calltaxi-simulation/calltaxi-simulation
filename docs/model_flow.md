# 모델 흐름도

서울 장애인콜택시 배차·운행 하루를 재생하는 이산사건 모델의 프로세스 흐름이다.
개체는 **콜**과 **차량** 둘이고, 아래 흐름은 두 개체가 만나는 지점(배차)을 축으로 그렸다.

가정 부호(A-01 · A-09 · A-11)의 정의는 [ASSA 로그](assa_log.md) 에 있다.

---

## 프로세스 흐름

```mermaid
flowchart TD
    S(["조별 차고지 출차"]) --> IDLE

    C(["콜 접수"]) --> Q["점수제 대기열"]
    Q -->|"인내심 초과"| X(["취소 · 이탈"])
    Q --> D{{"배차"}}
    IDLE["하차지 인근 제자리 대기"] --> D

    D --> M["공차 이동"]
    M --> B["승차"]
    B --> R["운행"]
    R --> O["하차"]
    O --> IDLE

    IDLE -->|"근무 종료"| E(["차고지 복귀"])

    style X fill:#f8d7da,stroke:#a94442
    style E fill:#e2e3e5,stroke:#6c757d
    style S fill:#d4edda,stroke:#3c763d
    style C fill:#d4edda,stroke:#3c763d
```

**읽는 법**

- 왼쪽 위 `조별 차고지 출차` 는 **차량**의 진입점, `콜 접수` 는 **콜**의 진입점이다.
- 두 개체는 `배차` 에서 만난다. 차량은 `하차지 인근 제자리 대기` 에서, 콜은
  `점수제 대기열` 에서 배차를 기다린다.
- `하차 → 제자리 대기 → 배차` 가 **순환 고리**다. 차량은 근무 시간 동안 이 고리를 돈다.
  **차고지로 돌아가지 않는다** — 하차한 자리 근처에서 다음 콜을 기다린다(가정 A-01).
- **이탈 경로는 하나다.** 대기열에서 인내심을 초과한 콜이 `취소·이탈` 로 빠진다.
  차량 쪽에는 이탈이 없다(고장·결행을 모델링하지 않는다).
- 차량은 근무 종료 시각에만 `차고지 복귀` 로 모델을 벗어난다.

## 조 편성 (실측 재구성, 차량-일 16.9만 건)

차량의 진입 시각과 근무 길이는 가정이 아니라 실측에서 역추정한 값이다(가정 A-09).
**차량-일 169,446건**(특장차 한정 · A-16)의 첫 승차·마지막 하차 분포이며, 산출 경로와
필터별 잔존 건수는 [provenance.md 8절](provenance.md) 에 있다.

| 조 | 출차 시각 | 차량-일 비중 | 조별 종료 중앙 | (구 · 전체) |
|---|---|---|---|---|
| 1조 | 07시 | **28.4%** | 14시 | 25.7% |
| 2조 | 08시 | **24.3%** | 15시 | 20.8% |

위 5개 시각이 차량-일의 **85.8%** 를 덮는다. 

**구 3조(10시 11.8%)가 사라졌다.** 임차택시는 첫 운행이 10시에 61.1% 몰린 단일
봉우리이고, 특장차만 보면 10시는 2.0%다. **그 봉우리는 임차택시 몫으로 보인다.**
특장차의 출차는 **07 / 08 / 12시 세 봉우리**이며 이것이 A-16(임차택시 분리)의 핵심
근거다. 두 체계를 섞으면 어느 쪽의 교대 구조도 재현되지 않는다.

**한계 — 확정할 수는 없다.** 대조 근거인 2012~13년 공문이 출차 07/08/10/12시를
적으면서 **차량 유형을 구분하지 않는다.** 공문이 전체 운영을 기술한 것이라면 10시가
빠지는 게 정합적이고, 특장차만을 기술한 것이라면 그 사이 운영이 바뀐 것이다. 어느
쪽인지 가릴 자료가 없다. **다만 07/08/12시가 공문과 그대로 일치하므로 시차 운행이라는
가정(A-09) 자체는 유지한다** — 흔들린 것은 조의 개수·시각 구성이지 시차 운행의
존재가 아니다.

**한계** — 가동시간을 첫 승차~마지막 하차로 잡으므로 출근 후 첫 콜까지와 마지막 하차 뒤
퇴근까지가 빠진다. **실제 출차는 이보다 이르고 귀고는 이보다 늦다.** 조 편성을 5개 조로
묶는 규칙은 코드에 없다 — 자세한 내용은
[`external_sources.md` B-7](external_sources.md).

**차량 대수는 723이 아니다.** 723은 연간 누적 고유 차량번호이고, 723은 연간 누적 고유 차량번호이고, 시뮬은 평일 574 / 주말 374를 요일별로 적용한다(metrics.daily_active_vehicles()).

## 단계 → 모듈·함수 대응

| 단계 | 담당 모듈·함수 |
|---|---|
| **조별 차고지 출차** | 거점 좌표·정원 `load.load_depots()` (44곳, 691대) / 조 편성 실측 `load.load_vehicle_trips()` → `metrics.vehicle_day_table()` / 차량 대수 `metrics.daily_active_vehicles()`. `simulator.allocate_fleet()` 이 배속 정원 비율로 일별 가동 대수를 나누고(최대잉여법, 거점당 최소 1대), `build_shifts()` 가 실측 분포에서 출차·종료 시각을 뽑는다 |
| **콜 접수** | `load.load_calls()` — 즉시콜·서울 필터 후 **1,222,330건**(특장차 한정 · A-16). 각 행의 `received_at` 이 도착 이벤트, `origin_dong_canon`·`origin_lat/lon` 이 발생 위치 |
| **점수제 대기열** | `CallTaxiSim._match_for_vehicle()` / `_match_for_call()` — 점수 = 접수순서 15 + 경과대기 35 + 거리 40(`SCORE_W`). 거리항은 좌표가 아니라 **이동시간(분)**, 탐색 반경은 직선거리 7 / 8 / 12km. **각 항은 후보 집합 안에서 정규화한다** — 절대 상한의 근거가 없어서다(A-18, 민감도 대상) |
| **배차** | 이벤트마다 국소 매칭 — 콜이 오면 그 콜에 맞는 차를, 차가 비면 그 차에 맞는 콜을 찾는다 |
| **공차 이동** | `travel_time.get_travel_time(출발동, 목적동, hour, is_weekend)` — 대기 위치 동 → 승차지 동. 3단 폴백(실측 OD → 거리대 속도 → 시간대 평균속도), 반환값 1~120분 |
| **승차 · 하차** | `CallTaxiSim._vehicle()` |
| **운행** | `travel_time.get_travel_time()` — 승차지 동 → 목적지 동. 공차 이동과 같은 테이블을 쓴다 |
| **하차지 인근 제자리 대기** | `CallTaxiSim._vehicle()` — 하차 후 위치를 목적동으로 옮기고 다음 배차를 기다린다(A-01). **유휴 ≠ 가용은 미반영** — 식사·교대·충전이 없어 유휴 차량이 전부 배차 가능하다 |
| **취소 · 이탈** | **실측 분류** `metrics.cancel_kind()` — 배차 전 + 1분 초과 취소를 `abandoned` 로 분류. **시뮬 샘플링** `outputs/patience_km.csv` — 인내심 KM 생존곡선에서 역CDF로 뽑는다(A-14). 접수 시 즉시 취소를 외생 확률 3.16% 로 먼저 뽑고, 나머지는 인내심 시각 전에 배차되지 못하면 취소한다. 배차 후 취소는 배차 시점에 3.74% 로 판정 |
| **차고지 복귀** | `CallTaxiSim._vehicle()` — 근무 종료 시 위치만 차고지로 되돌린다(이후 배차 대상 아님) |
| **하루 실행·로그 산출** | `CallTaxiSim.run()`, `run_placement(placement, calls, depots, travel_time, seed)`. 로그는 **입력 콜과 같은 컬럼 구조**라 `metrics` 를 그대로 통과한다 |
| **결과 채점** | `metrics.overall_metrics()` → `metrics.compare_to_target()` — 판정 5개(픽업 3 + 취소율 + 픽업 지니) 대조. 시뮬 로그도 실측 콜과 같은 함수를 통과한다 |

재생하지 않는 것은 `simulator.KNOWN_GAPS` 에 모아 뒀다 — 유휴≠가용, 조별 종료의
분포, 광역콜의 경기 체류, 차량 고장.

### 실행 성능과 재현도

**실행 시간**(공휴일 없는 주 기준, 이동시간 행렬 빌드 11초는 1회):
하루 4,065콜 0.5초 · 일주일 24,871콜 2.9초 · 한 달 100,942콜 17.4초.
약 5,800콜/초로 콜 수에 선형이라 **연간 재생도 4분 안쪽**이다. 재생 기간이
후보 개수를 제약하지 않는다.

**검증을 통과하지 못한다.** 판정 5개 중 픽업 지니만 허용오차 안에 들고, 픽업은
실측의 53%(중앙 9.45 vs 17.76분), 총 대기는 39% 수준이다. 원인은 매칭 미재현
(A-19)과 배차 선택(A-20)이며 **공급 부족은 아니다** — 동시 유휴가 θ 없이 이미
실측과 맞는다(163.5 vs 164.6대). 진단은 아래 절.

**그래도 후보를 돌린 이유** — 공간 구조가 재현되기 때문이다(픽업 지니 0.0805 vs
실측 0.0751). 동 간 격차 구조가 맞으므로 **후보 간 상대 비교는 유효하고**, 절감폭의

### 왜 대기가 짧은가 — θ 를 훑어보고 얻은 결론 (2026.08.09)

A-01 의 잔여 조치였던 **θ(유휴/비가용 임계)를 30~180분으로 훑었다.** 휴게 길이는
자유 파라미터로 두지 않고 실측 유휴 구간의 초과분에서 뽑았으므로(`IdleBreak`)
손잡이는 θ 하나다. 재생 구간은 2025-05-12 주.

| θ | 매칭 | 총 대기 | p90 | 취소율 | 포기 | 동시 유휴 최대 | 지니 |
|---|---|---|---|---|---|---|---|
| 없음 | 5.4 | 17.7 | 39.2 | 5.4% | 2.1% | **163.5** | 0.12 |
| 180 | 5.6 | 17.9 | 39.2 | 5.5% | 2.1% | 159.6 | 0.12 |
| 120 | 6.3 | 18.8 | 40.9 | 5.8% | 2.4% | 158.2 | **0.11** |
| 60 | 8.4 | 21.1 | 47.8 | 6.8% | 3.4% | 153.6 | 0.12 |
| 30 | 11.7 | 24.7 | 58.2 | 8.1% | 4.6% | 148.8 | 0.13 |
| 20 | 16.8 | 30.0 | 73.4 | 10.1% | 6.7% | 148.6 | 0.14 |
| 15 | 19.4 | 32.8 | 81.8 | 11.1% | 7.6% | 147.8 | 0.13 |
| **실측** | **24.8** | **43.6** | **83.7** | **16.6%** | **9.7%** | **164.6** | **0.10** |

**θ 는 원인이 아니다.** 세 가지가 그렇게 말한다.

1. **닿지 않는다.** 유휴 분의 55%를 걷어내는 θ=15 에서도 매칭 대기가 19.4분으로
   실측 24.8분에 못 미친다. θ 를 더 조이면 정상적인 운행 간 간격(실측 중앙 8.6분)
   까지 휴게로 읽게 되어 근거가 사라진다.
2. **독립 검사가 반대로 간다.** 동시 유휴 최대는 **θ 없음(163.5)이 실측(164.6)에
   가장 가깝고** θ 를 조일수록 멀어진다. 지니도 θ=120(0.11)이 가장 가깝고
   θ=20 에서 0.14 로 벌어진다. **대기만 맞고 나머지가 어긋나는 방향이다.**
3. **실측이 다른 곳을 가리킨다.** 실측 매칭 대기 분포에 **바닥**이 있다 —
   1분 안에 배차된 콜이 **0.33%**, p1 이 1.27분, p10 이 2.87분이다. 빈 차가
   있어도 즉시 배차되지 않는다는 뜻이다. 반면 이 엔진은 **콜의 78%를 접수
   즉시** 붙인다.

즉 부족한 것은 **공급량이 아니라 매칭 절차**다. 차량 가동률·동시 유휴는 이미
실측과 맞는데(θ 없음에서 163.5 vs 164.6) 배차만 3~4배 빠르다. 후보는 기사 수락
절차(자동수락 타이머)·배차 시각의 기록 정의·예약콜의 사전 점유이며, **어느 것도
현재 데이터로 가릴 수 없다.** 기구는 남겨두되(`simulator.IdleBreak`) 기본값은
꺼 둔다(`IDLE_BREAK_THETA_MIN = None`).

### 후보 필터율 — 채택하지 않음 (2026.08.09)

A-20(실제 배차는 가장 가까운 차를 고르지 못한다)을 모델링하려고 후보를 걸러 픽업을
늘리는 기구를 훑었으나 **기각했다.** `random 0.05` 가 픽업 분포를 정확히 맞추지만
**픽업 지니가 0.0805 → 0.0519 로 멀어진다** — 후보의 95%를 무작위로 버리면 '가까운
차가 있는 동'의 이점이 사라지고, 그 격차가 곧 거점 배치가 줄이려는 대상이다.
탐색 표와 근거는 [assa_log.md A-20](assa_log.md).

**끈 채로 둔다**(`CANDIDATE_KEEP_P = 1.0`). 남는 한계는 **픽업 수준의 미달**
(중앙 9.45 vs 17.76)이고, 뜻은 둘이다.

- **후보 간 순위·상대 비교는 유효하다** — 모든 후보가 같은 편의를 겪고, 공간 구조
  (픽업 지니)가 필터 없이 이미 실측과 맞는다.
- **절감폭의 절대 크기는 양방향 편의를 안고 있다** — 매칭·배차 미재현(A-19·A-20)은
  줄이는 쪽, θ 미도입(A-01)은 늘리는 쪽이고 상쇄 크기를 모른다. **절대값을 인용하지
  말고 후보 간 비교로만 읽는다.** 결과를 낼 때 이 문장을 함께 적을 것.

### 결과는 픽업 감소폭으로 읽는다 (2026.08.09)

**before/after 는 픽업(승차−배차) 기준으로 보인다.** 총 대기는 매칭 + 픽업인데
매칭이 상수처럼 깔려(재현 못 함, A-19) 총 대기로 보이면 개선폭이 희석된다 —
배치가 픽업을 3분 줄여도 총 대기로는 3/43 로 보인다. 채점 기준도 같이 옮겼다 —
`metrics.TARGETS` 는 **픽업 평균·중앙·p90 + 취소율 + 픽업 지니(0.0704)** 다.
총 대기 4개·매칭·**총 대기 지니(0.092)** 는 `REFERENCE_TARGETS` 로 내렸다.
**지니가 둘이니 인용할 때 어느 쪽인지 밝힐 것.**

**지니 분해가 그 결정의 근거다.**

| | 총 대기 지니 | 픽업 지니 | 매칭 지니 |
|---|---|---|---|
| 실측 | 0.1062 | **0.0751** | 0.1498 |
| 시뮬 | 0.0961 | **0.0805** | 0.2340 |

실측 총 대기 지니가 픽업 지니보다 높은 것은 **매칭이 공간 격차를 키우기 때문**이다
(0.1498). 차가 적은 지역에서 매칭도 오래 걸린다는 뜻인데, 우리 모델은 그 구조를
안 만든다(A-19). **재현하지 않기로 한 구간이 형평 점수로 넘어오면 안 된다.**

**픽업 격차의 출처를 갈라 봤다.** 대표 기간 재생 기준 시뮬 12.08분 vs 실측 18.80분.

| 원인 | 근거 | 몫 |
|---|---|---|
| **후보 풀이 깊고 최솟값을 고른다** | 접수 즉시 배차되는 콜에서 반경 안 후보가 **중앙 30대**(p25 13 · p75 55). 그중 최솟값은 **8.6분**인데 후보 중앙값 차량은 **22.3분**이다. **실측 픽업 중앙 17.8분은 최솟값보다 중앙값 쪽에 가깝다** | 대부분 |
| **셀 중앙값을 점추정으로 쓴다** | OD 셀의 중앙값을 그대로 돌려주므로 셀 안의 분산이 사라진다. 같은 효과가 운행 구간에서 직접 보인다 — 시뮬 23.5분 vs 실측 26.6분(**−11.5%**), 중앙은 19.7 vs 21.1 | 나머지 |

즉 **이동시간 표가 짧은 것이 아니라 배차가 지나치게 잘 고르는 것**이 주된 원인이다
(A-20). 실제 배차는 가장 가까운 차를 고르지 못하는데 — 기사 거절·사전 배정·차량
상태 등으로 후보가 걸러지는 것으로 보이나 근거 자료가 없다. A-19 와 같은 뿌리다.

**배차 후 취소를 넣은 뒤(2026.08.09)** 취소율은 5.40% → **8.78%** 로 올랐고
그중 배차 후 취소가 3.46%다(실측 3.82%). 나머지 격차는 전부 **대기 중 포기**
(시뮬 1.96% vs 실측 9.71%)이고, 그것이 곧 위의 매칭 지연 문제다.

정의된 시뮬 상수는 `SEED`, 탐색 반경 3종 + 평일 심야 `DISPATCH_RADIUS_PREDAWN`,
배차 가중치 `SCORE_W`, 조 편성 `SHIFT_TABLE`·`SHIFT_END`, 가동 대수
`FLEET_WEEKDAY`/`FLEET_WEEKEND`, 증차 대수 `NEW_DEPOT_VEHICLES`, 즉시 취소 확률
`IMMEDIATE_CANCEL_P` 다. **가중치·심야 반경·θ 는 `run_placement` 인자로도 받는다** —
민감도가 모듈 기본값을 건드리지 않고 갈아끼우려는 것이다(아래 「민감도」 절).

## 후보 평가 — 범위·지표·잡음 (2026.08.09)

배치안 5개를 대표 기간(30일)으로 시험 실행해 정한 것들이다. **경로는 정상이다** —
출력 컬럼 구조가 before 와 같고, 픽업이 5개 전부 줄었으며 승차 건수가 늘었다
(+100~150건). A-10 배분도 확인했다: 배속 정원 691 → 701 이면 가동 대수가 **평일
574 → 582대 · 주말 374 → 379대**로 늘고, 신규 거점이 **평일 8대 · 주말 5대**를 받으며
**기존 44곳 배속은 전부 그대로**다.

**증차는 정액이 아니라 비율이다.** `run_placement` 가 정원비
`701/691 = 1.0145` 를 내고 `int(round(base × scale))` 로 요일별 대수에 곱한다
(`simulator._build_vehicles`). 그래서 평일은 +8, 주말은 +5 다 — "신규 거점 10대"는
**배속 정원**이고, 그 거점이 그 날 실제로 받는 차는 가동 대수를 정원비로 나눈 몫이다.

244개 × 36회 = 110시간이라 불가능하다.

**공통난수로 줄일 몫은 이미 줄였다.** 콜 단위 난수는 call_id 로, 조 편성은 차량
슬롯 ID 로 고정했다 — 슬롯 ID 로 바꾸기 전에는 증차로 가동 대수가 574 → 582 가
되는 순간 전 차량 편성이 통째로 달라져 동별 픽업 잡음이 표준편차 0.465분이었다
(지금 0.039분, 12배 감소). 남은 변동은 **계 자체의 카오스**다 — 차 8대가 늘면
배차 순서가 바뀌고 그 뒤로 모든 궤적이 갈린다. 난수를 고정해도 남는다.

원인은 잡음이 아니라 **희석**이다. 8대는 574대의 1.4%인데 그 효과를 426개 동
전체로 나눠 보고 있었다.

### 평가 범위 — 거점에서 3km

같은 실행을 범위별로 다시 집계한 값이다(5개 후보 평균).

| 범위 | 동 수 | 콜 수 | before | Δ픽업 | σ | **신호/잡음** |
|---|---|---|---|---|---|---|
| 배정동 (1개) | 1 | 140 | 15.84 | −0.485 | 0.743 | **0.74** |
| **3km** | **25.4** | **4,427** | **13.15** | **−0.441** | **0.173** | **2.55** |

| 서울 | 432 | 99,263 | 12.01 | −0.058 | 0.049 | 1.29 |

**3km 를 쓴다. 근거는 효과 크기가 서울 평균의 7.6배(−0.441 vs −0.058)라는 것
하나다.** 희석이 문제였으므로(위 절) 범위를 좁혀 효과를 되살리는 것이 처방이다.
반경 3km 는 이미 진단 지표가 쓰는 공급 근접도와 같은 값이라(`metrics.SUPPLY_RADIUS_KM`),
"3km 안에 차가 없는 동"과 "거점을 놓아 3km 안에 넣는다"를 같은 자로 읽는다.

> **정정(08.09).** 여기 원래 "콜 4,427건이 모여 잡음이 억제된다"고 적혀 있었다.
> **그 전제는 데이터에서 확인되지 않는다.** 상위 50곳을 시드 3회로 돌려(자유도 2)
> 후보별 σ 와 범위 안 콜 수의 관계를 보니 `log(σ) ~ log(콜수)` 상관이 **+0.110**
> 으로, 1/√n 이 성립할 때 나와야 할 음의 관계가 없다. 콜 수 구간별 σ 중앙값도
> **0.68 / 0.86 / 0.95 / 0.55** (<2k / 2–3k / 3–4.5k / ≥4.5k)로 단조 감소하지
> 않는다. 시드 변동이 범위 안 콜의 표본오차가 아니라 **계 전체의 시드 동역학**
> (배차 순서가 갈리면 이후 궤적이 전부 갈린다 — 위 「공통난수」 절의 "남는 카오스")
> 에서 오기 때문으로 보인다. 그건 집계 범위를 넓혀도 줄지 않는다.
>
> **3km 채택 자체는 영향을 받지 않는다.** 채택 근거는 효과 크기 7.6배이고, 그
> 값은 이번 재검과 무관하게 그대로다. 위 표의 σ·신호/잡음 열은 5개 후보로 잰
> 실측치라 값 자체는 유효하지만, **"콜이 모이면 σ 가 준다"는 인과로 읽지 말 것.**
>
> **↑ 이 정정은 08.10 에 다시 뒤집혔다.** 244곳 전부로 재니 상관 −0.169(절대 Δ
> 기울기 −0.423)로 관계가 나타난다. 위 판단은 상위 50곳이라는 좁은 부분집합에서
> 나온 것이었다. 「증차 규모는 10대 고정」 절의 **「정정의 정정」** 참조.

**3km 는 집계 범위이지 계산 단위가 아니다.** 시뮬은 여전히 동 단위로 돌고
(차량 위치·이동시간·배차 전부 동 기준), 결과를 읽을 때 **거점에서 3km 안에 드는
동들(평균 25.4개)의 픽업을 모아 보는 것**뿐이다. 3km 원 안을 하나의 격자로 다루는
것이 아니다.

**배정동 하나로 좁히면 오히려 못 쓴다.** 효과는 −0.485분으로 가장 크지만 σ 가
0.743 으로 튀어 신호/잡음이 0.74 로 내려간다. **표본이 없어서다** — 30일 동안 필동
53건 · 명동 245건뿐이라 동 평균이 크게 흔들린다. 그 두 후보는 배정동 Δ 가 −0.005 ·
+0.011 로 사실상 0 이 나오는데, 효과가 없어서가 아니라 재지 못해서다.

이 판단은 위 정정과 어긋나지 않는다. **콜 140건과 4,427건 사이에서는 표본오차가
지배하지만(σ 0.743 → 0.173), 3km 범위 안쪽의 666~11,776건 구간에서는 더 이상
줄지 않는다.** 표본오차가 시드 동역학 아래로 내려가는 지점이 그 사이 어딘가에
있다는 뜻이다. 배정동을 버리는 근거는 유효하고, "더 모으면 더 조용해진다"는
확장만 성립하지 않는다.

### 총 대기도 함께 재되 참고 열이다 (2026.08.12)

픽업만 내면 **"그래서 이용자가 체감하는 시간은 얼마나 줄어드나"에 답이 없다.**
이용자가 겪는 것은 접수부터 승차까지(총 대기)이고 픽업은 그 뒷도막이다. 그래서
같은 3km·같은 시드로 총 대기 before/after 를 함께 재어 `rate_total_pct` 로
남긴다(`evaluate.scope_wait_total`). **재생 비용은 늘지 않는다** — 이미 돌린
로그를 한 번 더 훑을 뿐이다.

**절대값은 인용할 수 없다.** 대표 3곳(개선율 rank 1 / 122 / 244)을 같은 기간·같은
범위의 실측과 맞대 본 값이다.

| 후보 | 실측 총 대기 | 시뮬 before | 배수 |
|---|---|---|---|
| 411 마천동1 (rank 1) | 42.3분 | 18.7분 | **0.44배** |
| 240 구립서대문노인전문요양센터 (rank 122) | 43.3분 | 18.1분 | **0.42배** |
| 598 당산노외 (rank 244) | 46.4분 | 15.3분 | **0.33배** |

매칭을 재현하지 않으므로(A-19) 총 대기가 구조적으로 짧다 — 위 「결과는 픽업
감소폭으로 읽는다」 와 같은 뿌리다. **그래서 화면에는 개선율(%)만 낸다.** 분
단위를 보이면 진단 화면의 실측 대기(서울 평균 42.7분)와 견주게 되는데 그 비교는
성립하지 않는다. 원값(분)은 `placement_eval.csv` 에만 둔다.

**순위·판정 기준은 픽업 그대로다.** 총 대기 개선율이 픽업보다 크게 나온다.

| 후보 | 픽업 개선율 | 총 대기 개선율 | 배수 |
|---|---|---|---|
| 411 (rank 1) | −8.57% | **−10.99%** | 1.28배 |
| 240 (rank 122) | −2.91% | **−4.45%** | 1.53배 |
| 598 (rank 244) | −1.48% | **−3.29%** | 2.23배 |

**보기 좋다고 기준을 옮기면 결과를 보고 규칙을 바꾸는 것이 된다.** 2단계 컷도
등급 규칙도 픽업 기준으로 사전 고정돼 있다(위 「개선율과 수혜 규모를 함께 낸다」
와 같은 논리). 배수가 후보마다 1.28~2.23 으로 다르므로 **순위가 실제로 달라진다** —
그래서 더더욱 옮기지 않는다. 겹침(`n_overlap`)도 픽업 구간으로만 계산하므로 총
대기에는 대비 구간을 붙이지 않는다. 시드 간 σ 만 낸다.

#### 총 대기 Δ 는 보수적이다

**분모가 픽업과 다르다.** 픽업은 배차된 콜, 총 대기는 **승차까지 간 콜**이다.
거점을 놓으면 포기가 줄어 승차 건수가 늘고(411 기준 시드 평균 +8.3건), **새로
타는 콜은 원래 오래 기다리던 건**이라 after 평균을 끌어올린다. 즉 이 통로는
개선을 **줄여서** 보이게 한다.

크기를 재 두었다. 새로 타는 콜이 60분(장기 대기 문턱)을 기다렸다고 놓으면
`8.3 × (60 − 16.62) / 1,794 = 0.20분` 으로, **Δ −2.05분의 10%** 다. 상한이므로
실제로는 이보다 작다. 승차 건수는 `n_boarded_before`·`n_boarded_after` 로 후보마다
남겨 두었으니 다른 후보에서도 같은 계산을 할 수 있다.

**반대로 미는 통로는 확인되지 않았다.** 그래서 이 항목만은 방향을 말할 수 있다 —
절감폭 전체에 대한 「양방향 편의」(아래 「결과를 인용할 때」)와는 다른 이야기다.
그쪽은 여전히 두 방향이 다 있고 상쇄 크기를 모른다.

#### 대기 중 포기·60분 초과는 내지 않는다

같은 실행에서 함께 재 봤지만(대표 3곳 × 시드 3회) 둘 다 화면에 올리지 않는다.

**대기 중 포기 — 후보에 따라 신호가 갈린다.** rank 1 은 −9.0±1.7건, rank 244 는
−8.3±2.9건으로 쓸 수 있는데 **rank 122 는 −3.0±3.0건이고 시드 42 에서는 0건**이다.
후보별로 표시 여부를 가르면 결과를 보고 규칙을 정하는 것이 되므로 일괄 제외한다.

**60분 초과 — 3곳 중 2곳에서 시드마다 부호가 뒤집힌다**(rank 122 +2/−10/+1,
rank 244 +5/−8/−4). 시뮬 수준이 실측의 1/5~1/40 이라(위 표와 같은 대조:
0.20 / 0.05 / 0.02배) **60분이라는 절대 문턱을 넘는 건이 구조적으로 거의 생기지
않는다.** 문턱 지표는 분포가 통째로 왼쪽에 있으면 잴 것이 남지 않는다.

원자료와 스크립트를 남겼다 — `outputs/page3_extra_raw.csv`(대표 3곳 × 시드 3회 ×
before/after, 지표 10종)와 그것을 만든 `analysis/page3_extra.py` · 실측 대조를 낸
`analysis/page3_actual.py`. **대표 3곳은 개선율 rank 1 / 중앙 / 최하로, 표를 보기
전에 정한 규칙이다**(`PICKS = [1, (n+1)//2, n]`). 좋아 보이는 후보를 고른 것이
아니다.

### 3km 콜이 2,000건 미만이면 「표본 부족」으로 표시한다

`evaluate.MIN_CALLS_SCOPE = 2000`. **계산에서 빼지 않는다 — 표시만 한다.**

**잡음 기준이자 수혜 규모 기준이다.** 값 자체는 3km 채택 근거였던
4,427건·신호/잡음 2.55 에서 S/N 1.7(2.55 의 2/3)을 목표로 `4,427 × (1.7/2.55)²
≈ 1,967` 로 유도했고, **어느 후보가 걸리는지 보기 전에 정했다.** 244곳으로 다시
재니 σ 가 실제로 콜 수와 함께 줄어(「정정의 정정」) **이 유도가 되살아났다** —
표본 부족 12곳의 대비 구간 폭 중앙이 2.87%p 로 정상 232곳의 1.68%p 보다 넓다.

**그리고 이것도 뜻한다 — 개선율은 몇 사람에게 닿는지를 담지 않는다.** 개선율은
출발점 픽업으로만 정규화한 값이라, 3km 안 콜이 666건인 곳의 −8.2% 와 6,000건인
곳의 −3% 가 표에서 같은 무게로 보인다. 앞의 것은 뒤의 것보다 혜택이 닿는 사람이
한참 적다. 유도값을 기준으로 남겨 두되 근거를 이렇게 읽는다.

### 개선율과 수혜 규모를 함께 낸다

**개선율만으로 정렬하면 범위가 좁은 후보가 위를 차지한다.** 실제로 그렇게 됐다 —
2단계 50곳에서 개선율 상위 10 중 6곳이 표본 부족이었고, **244곳 전부로 돌린
뒤에도 상위 10 중 6곳 그대로다**(전체로는 12곳·4.9%). 아래 「실행 결과」 참조.

그래서 후보마다 **총 절감 분**(`delta × 범위 콜수`, 곧 범위 안에서 사라진 총 대기
분)을 개선율 옆에 나란히 낸다. 이것은 가중치가 임의인 복합 지표가 아니라 단위가
있는 물리량이다. **그래도 이쪽으로 정렬하지 않는다** — 편향이 반대로 걸릴 뿐이다.
개선율은 범위가 좁은 곳을, 총절감은 콜이 많은 도심을 위로 올린다. 어느 하나를 주
정렬로 삼으면 반드시 그 방향으로 오독된다. **둘을 나란히 두고 읽는다.**

정렬 키는 개선율 그대로다. 2단계 컷 50과 등급 규칙이 개선율 기준으로 사전 고정돼
있어, 지금 정렬을 바꾸면 사후 선택이 된다. 총절감 표는 **대조용으로 병기**한다.

### 등급은 계산하되 표시하지 않는다 (08.10 변경)

**244곳 결과를 보고 등급 표시를 뺐다.** 규칙(`assign_grades`)과 열은 그대로 남아
있고 CSV 에서는 `ref_grade` · `ref_gap_prev` · `ref_threshold_prev` 로 이름을 바꿔
맨 뒤 참고 열로 내렸다. 보고 표에는 나오지 않는다.

**사유 셋.**

1. **판단을 대신하는 표시라 도구의 성격과 어긋난다.** 이 산출물은 실무자에게
   선택을 열어 두려는 것이다. 등급 한 글자는 그 선택을 미리 내려 준다.
2. **240곳이 [하] 하나로 뭉쳐 표시가 정보를 담지 못한다.** 244개 인접 경계 중
   문턱을 넘은 곳이 4위/5위 한 곳뿐이었다(gap 0.93%p). 나머지 239개 경계는 중앙
   gap 0.012%p 로 문턱(중앙 1.97) 근처에도 못 간다.
3. **결정적으로, [상] 4곳 중 3곳이 표본 부족이다.** "최고 등급"이 **가장 좁은
   지역을 가리켰다.** 이 표시를 그대로 두면 실무자가 비율만 큰 후보를 고른다.
   아래 「실행 결과」의 표본 크기 편향 항목이 그 메커니즘이다.

**규칙을 지우지는 않았다.** 등급 규칙은 결과를 보기 전에 고정한 것이라, 결과를
보고 지우면 그 자체가 사후 선택이다. **불편한 것은 규칙이 아니라 표시였으므로
표시를 고쳤다** — 이 문서가 아래에서 이미 적어 둔 처방과 같은 방향이다.

**대신 후보마다 이 넷을 낸다.**

| 무엇 | 열 | 답하는 질문 |
|---|---|---|
| 개선율 ± 대비 구간 | `rate_pct` · `interval` | 얼마나 좋은가 / 얼마나 확실한가 |
| 콜 · 동 · 총절감 | `n_calls_scope` · `n_dong_scope` · `total_delta_min` | 몇 명에게 닿는가 |
| 표본 부족 표시 | `sample_ok` | 이 비율을 믿어도 되는가 |
| **겹치는 후보 수** | `n_overlap` | 이 순위를 말할 수 있는가 |

`n_overlap` 이 등급이 하던 일("얘는 어느 무리인가")을 대신한다. 등급과 달리
**인접 간격이 아니라 그 후보 자신의 구간**을 보므로 후보가 촘촘히 깔려도 뭉개지지
않는다 — 0 이면 단독으로 갈리고, 232 면 사실상 아무 말도 할 수 없다는 뜻이다.

아래 절은 등급 규칙 자체의 근거이고 **규칙은 그대로 유효하다.** 표시만 빠졌다.

### (규칙 근거) 등급은 나눌 수 있고 순위는 못 매긴다

최고(−0.775)와 최저(−0.208)의 차이 0.567 은 σ(~0.19)의 **3배**라 분명히 갈린다.
그러나 **1·2위는 못 가른다** — 구립서초(−0.775) vs 중앙로(−0.710)의 차이 0.065 는
σ 안에 들어간다.

**그래서 결과를 순위표로 내지 않는다.** 실무자가 순위를 절대적으로 읽으면 근거
없는 선택을 하게 된다 — 2위를 3위보다 낫다고 볼 수 없는데 표가 그렇게 보이면 그
차이가 판단에 들어간다.

당시 처방은 **등급으로 묶고 "이 등급 안에서는 우열을 가릴 수 없다"를 함께 적는
것**이었다. 08.10 에 그 표시를 **대비 구간 + 겹침 수**로 바꿨다(위 절) — 문제
의식은 같고 표시만 다르다. 등급은 판단을 대신 내려 주는데, 겹침 수는 "몇 곳과
구분되지 않는지"만 말하고 선택은 남겨 둔다.

**등급은 인접 간격만 본다 — 하나로 뭉칠 수 있다.** 후보가 촘촘히 깔리면 양 끝이
크게 벌어져 있어도 중간에 문턱만 한 빈틈이 없어 한 등급이 된다. 그때 "구분이 안
된다"가 정직한 보고이지 규칙의 결함이 아니다. 그래서 등급과 **함께 후보별 대비
구간을 낸다** — 등급이 뭉쳐도 구간이 안 겹치는 쌍은 우열을 말할 수 있다.

**대비 구간은 신뢰구간이 아니다.** 반폭은 `k/√2 · σ = 1.41σ` 로, σ 가 같을 때
"두 구간이 안 겹친다"와 "등급이 갈린다"가 **정확히 같은 말이 되도록 등급 규칙에서
유도한 폭이다.** 표에서 눈으로 읽은 것과 등급이 어긋나지 않게 하려는 것이지 95%
같은 신뢰수준을 뜻하지 않는다. σ 자체는 `rate_sd` 열에 따로 남긴다.

σ 를 평균의 표준오차(σ/√n)로 바꾸면 문턱이 √3 배 낮아져 더 잘게 갈린다. **쓰지
않는다** — 등급이 뭉친 결과를 보고 규칙을 바꾸는 것이라 사후 선택이다. 규칙이
불편하면 규칙이 아니라 **표시**를 고친다. 대비 구간이 그 처방이다.

### 증차 규모는 10대 고정

A-10 대로 **10대다. 시뮬 파라미터로 두지 않는다** — 배정 단위 10대에는 문서
근거가 있고(A-08), 규모를 바꿀 수 있게 두면 **증차량이 상수라는 전제가 깨져
"후보별 차이는 위치에서만 나온다"는 해석이 무너진다.** `resolve_placement` 는
넘겨받은 배속 값을 쓰지 않고 언제나 `NEW_DEPOT_VEHICLES` 로 덮는다.

10대에서도 3km 범위면 후보 간 차이가 잡힌다. **신호/잡음은 244곳 × 시드 3회
실측으로 주 지표(개선율) 기준 중앙 5.10(IQR 3.43~8.42, 10~90%ile 2.23~15.56,
최소 1.10)이고 1 미만인 후보는 없다.** 절대 Δ 기준으로 재도 중앙 5.04
(IQR 3.36~8.13)로 사실상 같다.

> **갱신(08.10).** 여기 원래 "2.9~4.1"이라고 적혀 있었다. 그 범위는 5개 후보
> 시절 값으로, 실제로는 그중 둘(구립서초 4.11 · 중앙로 2.90)만 가리켰다 —
> 나머지 셋은 1.33~2.85 로 아래에 있었다.

> 평균적으로 약 11% 과소추정한다(c4 = 0.886). 보정하면 σ 중앙 0.674%p ·
> **S/N 중앙 4.52** 다. 그만큼 깎아 읽을 것.

> **정정의 정정(08.10) — σ 는 콜 수와 함께 준다.** 위 「평가 범위」 절의 정정은

> 잡음은 줄지 않는다"고 적었다. **244곳 전부로 다시 재니 관계가 나타난다** —

> **−0.423** 으로 1/√n 이 뜻하는 −0.5 에 가깝다). 콜 수 구간별 σ 중앙도
> **1.014 / 0.795 / 0.777 / 0.540**(<2k / 2–3k / 3–4.5k / ≥4.5k)로 단조 감소한다.

> 사후 선택이다. 표시의 의미는 이제 **잡음과 수혜 규모 둘 다**로 읽는다.

#### 개선율 순위는 표본 크기의 함수다

표본 부족(3km 콜 < 2,000건)은 전체 **12곳(4.9%)** 인데 **개선율 상위 10 중
6곳(60%)** 이다. 상위 20 중 7곳, 상위 50 중 10곳 — 12곳 가운데 10곳이 상위 50에
들어간다. 무작위 분포가 아니다.

| | 표본 부족 12곳 | 정상 232곳 |
|---|---|---|
| 평균 개선율 | **−5.86%** | −3.14% |
| 대비 구간 폭 중앙 | **2.87%p** | 1.68%p |
| 3km 콜 중앙 | 1,721 | 4,846 |

**콜이 적으면 분모가 작아 비율이 튀고 구간도 넓어진다.** 개선율 상위권은 상당
부분 이 효과로 설명된다. **총절감 순위에는 표본 부족이 한 곳도 없다**(상위
10·20·50 모두 0) — 총절감은 규모를 곱해 읽으므로 같은 편향이 걸리지 않는다.

#### 두 순위는 다른 것을 잰다

**Spearman ρ = +0.32.** 개선율 상위 20 과 총절감 상위 20 이 **4곳만 겹친다**
(상위 10 은 1곳, 상위 50 은 17곳). 개선율 상위는 콜 1,500~3,000대에, 총절감
상위는 4,500~10,000대에 몰린다.

- 개선율 3위 **577 내곡동은 총절감 234위다** — 동 2개·콜 666건이라 비율은
  −8.24% 지만 실제로 줄어드는 총 대기는 879분뿐이다.
- 총절감 1위 **607 명일파출소**(−2,954분)는 개선율로는 18위다.
- 개선율은 "그 지역 이용자가 평균 얼마나 덜 기다리나", 총절감은 "얼마나 많은
  사람에게 닿나"를 잰다. **어느 하나로 정렬해도 그 방향으로 오독된다.**

#### "1위"는 이 데이터에서 지지되지 않는다

개선율 1위 **411 마천동1**(−8.57% ± 2.14%p)은 **다른 24곳과 대비 구간이 겹치고,
그 안에 개선율 47위까지 들어간다.** 1위보다 확실히 나은 후보도(`rate_hi <` 1위의
`rate_lo` 인 곳 0), 1위가 확실히 나은 후보도 그 24곳 중에는 없다. **말할 수 있는
것은 25곳이 한 덩어리라는 것뿐이다.**

반면 **2위 380 강일동**(−8.27% ± 0.38%p)은 겹치는 곳이 4곳뿐이고 총절감도
−2,607분(전체 9위)으로 크다. **구간이 좁고 두 시선에서 모두 상위인 후보다.**
다만 이것은 사전 고정된 규칙의 산출물이 아니라 표를 읽은 결과이므로, 선정 근거로
쓰려면 그 사실을 밝혀야 한다.

겹침 수는 후보마다 크게 다르다 — 411 은 24곳, 615 사당노외는 160곳, 515 비봉과
366 압구정은 **232곳**(전체의 95%)과 겹친다. σ 가 큰 후보일수록 아무 말도 할 수
없다는 뜻이고, `n_overlap` 열이 그것을 한 숫자로 보여 준다.

### 결과를 인용할 때 반드시 함께 적을 것

**절감폭의 절대 크기는 양방향 편의를 안고 있다.** 매칭·배차 미재현(A-19·A-20)은
절감을 줄이는 쪽이고, θ 를 두지 않은 것(A-01)은 늘리는 쪽이다. 두 편의가 상쇄되는
크기를 알 수 없으므로 **절대값을 인용하지 말고 후보 간 비교로만 읽는다.**

> **정정(08.10).** 여기 원래 "픽업 수준이 실측의 53%라 −0.44분도 그만큼 축소된
> 값이고 실제로는 더 클 가능성이 높다"고 적혀 있었다. **한쪽 편의만 센 것이라
> 틀렸다.** θ 민감도(아래 「민감도」 절)에서 θ=60 이면 대표 9곳 평균 개선율이
> −3.71 → −3.05%(**−18%**), 최상위 380 은 −8.29 → −5.94%(**−28%**)로 줄었다 —
> **θ 를 끈 것이 절감을 부풀리는 쪽**이다. 두 방향의 크기를 모르므로 "실제 절감은
> 더 크다"는 결론은 근거가 없다. 픽업 재현 53%는 사실로 남기되 절감폭의 부호를
> 가리키는 근거로 쓰지 않는다.

**후보 간 상대 비교는 유효하다** — 모든 후보가 같은 편의를 겪고 공간 구조
(픽업 지니)가 실측과 가깝다.

**그리고 개선율만 인용하지 말 것.** 개선율은 표본 크기에 끌려 올라간다(아래
「실행 결과」). 인용할 때는 **콜 수 · 총절감 · 겹침 수**를 함께 적는다.

**⑴ 개선율이 큰 쪽과 작은 쪽은 어느 설정에서도 갈린다. 다만 상위권 안에서 몇 곳을

설정 전부에서 앞쪽 3자리에 있지만, **근접 강화에서는 3위와 4위의 간격이 4.12 →
0.59%p 로 좁아진다** — σ 수준이다. **"상위 몇 곳"이 뚜렷해 보이는 인상 자체가
가중치에 달렸다는 뜻이다.**

> **그래서 이 문서는 "상위 3곳"이라는 표현을 쓰지 않는다.** 등급·순위를 표시하지
> 않기로 한 것과 같은 이유다(「등급은 계산하되 표시하지 않는다」 절) — 몇 곳을
> 묶어 보여 주는 순간 그 경계가 판단을 대신 내려 준다. 위 표의 「앞쪽 3자리」는
> **민감도를 재기 위해 밴드를 사전 고정한 결과**이지 상위권의 크기에 대한 주장이
> 아니다.

**⑵ 중·하 6곳의 순서는 설정이 정한다.** 심야 반경만 7km 로 바꿔도 그 6곳의 순위
상관이 **−0.029** 로 무작위가 된다. 416 약수동은 기본에서 9위(꼴찌)인데 심야
7km 에서 **4위**로 다섯 칸 올라온다.

**⑶ 그런데 그 6곳은 본실행에서도 이미 구분되지 않았다.** 겹침 수가 147~224곳
(전체의 60~92%)이다. **민감도가 새 문제를 드러낸 게 아니라 `n_overlap` 이 하던
말을 다른 경로로 확인한 것이다** — 구간이 겹치는 후보끼리는 우열을 말할 수 없고,
설정을 흔들면 그 말할 수 없음이 순서 뒤집힘으로 나타난다.

**⑷ 절대 크기는 θ 에 의존한다.** θ=60 이면 9곳 평균 개선율이 −3.71 → **−3.05%**
(−18%)로 줄고, 개선율이 가장 큰 380 은 −8.29 → −5.94%(**−28%**)로 준다. 증차한
10대도 함께 쉬므로 공급 증분이 희석되기 때문이다. **θ 를 켤 근거가 생기면
"몇 % 준다"는 숫자를 다시 내야 한다. 순위는 그대로다.**

**이것이 위 「결과를 인용할 때」 절을 고친 근거다.** θ 를 끈 것은 절감을 **부풀리는**
쪽이고 A-19·A-20 은 **줄이는** 쪽이라, 편의가 양방향이다.

**⑸ 가중치는 기준선을 옮긴다.** 현행 배치의 3km 픽업(9곳 평균)이 근접 강화에서
**−0.41분**, 대기 강화에서 **+0.43분** 움직인다. 가까운 차를 우선하면 픽업이
짧아지는 당연한 방향이고, 크기는 기준선 ~12분의 약 3.5%다. **개선율은 그 설정
안의 before 대비라 이 이동에 상쇄된다** — 그래서 ρ 가 0.95/0.92 로 높게 남는다.

**⑹ 심야 반경은 수준을 안 바꾸고 순서만 흔든다.** 기준선 이동이 **−0.045분**으로
사실상 0 이다(A-17 이 "영향은 작다"고 적은 그대로 — 심야 콜 1.9%). 그런데도
개별 후보의 Δ 는 최대 0.24분 움직인다. **이것은 심야의 직접 효과가 아니라 계의
카오스다** — 새벽에 어느 차가 어디 있느냐가 갈리면 그날의 배차 궤적이 전부
갈린다(「공통난수」 절의 "남는 카오스"). 효과가 −0.08~−0.3분인 하위 후보에서는
그 흔들림이 순위를 뒤집기에 충분하다.

### 남는 한계

- **n=9 의 Spearman 은 거칠다.** ρ=0.95 는 "9곳 안에서 한 쌍이 바뀌었다"는 뜻이지
  244곳 전체 순위가 그만큼 보존된다는 뜻이 아니다. ⑴ 의 밴드 진술이 더 강하다.
- **시드 1회라 설정별 σ 가 없다.** 설정 간 차이를 본실행의 σ 와 견줄 뿐이고,
  그 σ 는 n=3 추정이라 약 11% 과소추정 쪽이다(c4=0.886).
- **A-18 민감도는 배차의 일부만 흔들었다.** 가중치는 **차량 쪽 매칭**
  (`_match_for_vehicle`)에서만 문다 — 콜 하나에 차를 붙일 때는 접수순서·경과대기가
  상수라 거리항만 순위를 가른다(`_match_for_call`). 이 손잡이로 덮이지 않는 배차가
  남는다.
- **세 가정만 흔들었다.** A-19(매칭 미재현)·A-20(이동시간 최소 선택)은 손잡이가
  아니라 구조라 이 틀로 흔들 수 없다. 절감을 **줄이는** 쪽 편의는 그쪽에서 온다.

## 엔진·난수

엔진이 쓰는 난수·이벤트 설계다.

### DES 엔진

| 항목 | 값 |
|---|---|
| 소프트웨어 | **SimPy 4.1.2** (오픈소스 Python 라이브러리) |
| 이벤트 처리 방식 | **process interaction** |
| 사용 위치 | `CallTaxiSim.__init__` 이 `simpy.Environment()` 를 만들고, 차량 한 대의 하루를 `_vehicle()` 프로세스로, 콜 접수를 `_call_source()` 프로세스로 둔다 |

SimPy 는 파이썬 제너레이터를 프로세스로 삼아, 프로세스가 이벤트를 `yield` 하면 중단하고
스케줄러가 시간순 이벤트 큐에서 다음 이벤트를 꺼내 재개시킨다. 이 모델에서는 **차량
1대가 하나의 프로세스**이고 `대기 → 배차 → 픽업 이동 → 탑승 → 운행 → 하차 → 대기` 를
한 제너레이터 안에서 진행한다 — 위 흐름도의 순환 고리가 그대로 코드 구조가 된다.

### 난수 생성기

| 항목 | 값 |
|---|---|
| 생성기 | `numpy.random.default_rng(seed)` → `numpy.random.Generator` |
| 비트 생성기 | **PCG64** (Permuted Congruential Generator, 128비트 상태 / 64비트 출력) |
| **Mersenne Twister 아님** | MT19937 은 레거시 `numpy.random.RandomState` 의 기본이다. 이 저장소는 `default_rng` 를 쓰므로 PCG64 다 |
| 확인 방법 | `np.random.default_rng().bit_generator.state['bit_generator']` → `'PCG64'` |
| 사용 위치 | `CallTaxiSim.__init__` — `self.rng = np.random.default_rng(seed)` |
| 시드 | `simulator.SEED = 42` |

SimPy 자체는 난수를 만들지 않는다 — 이벤트 스케줄링만 한다. 확률 표본은 전부 NumPy
`Generator` 에서 나온다.

### 시드 배분·공통난수 — 미정

인스턴스마다 `default_rng(seed)` 로 생성기를 **하나** 만들어 즉시 취소·인내심·조
편성이 같은 스트림을 나눠 쓴다. 아래는 후보 비교 단계에서 정해야 한다.

| 항목 | 상태 |
|---|---|
| 샘플링 프로세스별 스트림 분리 | **미정.** 인내심 분포·이동시간 잔차·조 배정 등을 별도 스트림으로 가를지, 단일 생성기를 공유할지 |
| 공통난수(CRN) 사용 여부 | **미정.** 배치안 A와 B를 비교할 때 같은 난수열을 쓸지 |
| 배치안 간 시드 배분 규칙 | **미정** |
| 반복(replication) 수와 시드 목록 | **미정** |

배치안 비교의 분산을 줄이려면 CRN 이 유리하다. **단일 스트림을 공유하는 지금
구조에서는 배치안이 바뀌면 이벤트 순서가 달라져 인내심 표본도 함께 흔들린다** —
후보 간 차이에 그 흔들림이 섞여 들어오므로, 비교를 시작하기 전에 스트림을 갈라야
한다. 결정 전까지 고정된 사실은 **`SEED = 42` 단일 시드, PCG64 단일 스트림**뿐이다.

## 모델 경계

흐름도가 다루지 **않는** 것 — 폭과 깊이를 가늠하는 데 필요하다.

| 항목 | 처리 |
|---|---|
| 예약콜 | 재생하지 않는다. 시간대별 실측 수행 건수를 기반으로 가용 차량에서 차감만 한다(가정 A-11). 즉시콜 필터로 원본의 12.11%(168,421건)가 입력에서 빠진다 |
| 서울 밖 출발 콜 | 입력에서 제외(즉시콜 중 218건) |
| 서울 밖 목적지 | **포함한다.** 운행은 재생하되 목적동 좌표가 없으면 이동시간 폴백으로 처리(전체의 7.37%) |
| 차량 고장·결행 | 모델링하지 않는다 |
| 기사 휴게 | 별도 활동으로 두지 않는다. 실측에서도 분리할 근거가 없다 |
| 억제된 수요 | 접수된 콜만 센다. 대기가 길어 아예 부르지 않게 된 수요는 어떤 지표로도 보이지 않는다 |
| 차량 유형 구분 | **원본이 특장차 한정본이라 구분할 것이 없다**(A-16). 임차택시는 차고지 기반 교대 운영이 아니어서 거점 배치의 영향을 받지 않으므로 모집단에서 뺐다 |
