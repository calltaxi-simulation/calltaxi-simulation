# 코드 밖 근거

이 저장소의 코드로 재현되지 않는 근거를 모은 문서다. 문헌·구술 자료, 코드 밖에서
수행돼 사후에 정리한 기록(소급 기록), 받지 못한 자료의 사유, 그리고 저장소 밖에 있는
스크립트·노트북이 여기 들어간다.

**코드로 재현되는 것은 여기 없다** — 필터 정의·지표 정의·산출 방식은
[`calibration.md`](calibration.md), 산출된 값은 [`provenance.md`](provenance.md) 에 있다.
**가정 부호(A-xx)의 정의도 여기 없다** — [`assa_log.md`](assa_log.md) 가 정본이다.

### B-4. STL 분해·EDA — 2026-07-25 (소급 기록 · **노트북 확인**)

> **⚠ 확인 필요 — 원작성자 확인 전까지 아래 수치를 인용하지 말 것.**
> 두 가지가 서로 맞지 않는다. ① `대기분` 을 **배차 − 예정**으로 정의하면서 즉시콜 필터를
> 걸지 않은 전수를 썼다고 돼 있는데, 예약콜이 섞이면 예정시각이 접수보다 한참 뒤라 값이
> 뒤틀려야 한다. 그런데 결과 18~21분은 오히려 필터를 건 `wait_match_mean`(20.82분)과
> 비슷하다. ② 요일별 건수를 상한으로 잡아도(평일 25~27만 × 5 + 주말 9~10만 × 2)
> 약 155만인데 대상이 "전수 1,729,476행"으로 적혀 있다. 오히려 필터 후 1,527,213건에
> 가깝다. **아래 값은 원문 그대로 두었고 이 항목만 표시로 남긴다.**

| 항목 | 내용 |
|---|---|
| 대상 데이터 | `서울시설공단_장애인콜택시 탑승내역_20251231.csv` 원본 1,729,476행 (**필터 없음** — 즉시콜·서울 컷을 걸지 않은 전수) |
| 가공 내용 | 일별 콜 수 시계열을 `asfreq('D').interpolate()` 로 결측일 보간 후 STL 분해(`period=7`, `robust=True`), 정상성 검정, 요일·시간대 분포 |
| 제외·변경 건수 | 원본을 변형하지 않는 분석이라 제외 0건. 결측일 보간만 값 변경에 해당한다 |
| 산출물 위치 | `disabledCalltaxi_EDA.ipynb` (셀 18개, 출력 포함 저장). 저장소 밖 — 5절 참조 |
| 근거 | 노트북 셀 13(STL) · 14(해석) · 15(정상성) · 17(요일별 건수·대기)에서 아래 결과가 출력과 함께 확인된다 |

**노트북에서 확인되는 결과**

| 셀 | 내용 | 결과 |
|---|---|---|
| 13–14 | STL 분해 (`statsmodels.tsa.seasonal.STL`, period=7, robust) | **주간 계절성이 지배적** — 평일 +700 ↔ 주말 −2,000, 진폭 2,500 이상(전체 수준 ~4,000의 절반 이상). 추세는 연중 안정(1월 ~4,000 → 6~10월 ~4,500). 연휴(설·5월 초·추석)는 계절성이 아니라 **잔차의 −2,000~−3,000 이상치**로 잡힌다 |
| 15 | 정상성 검정 | ADF p = 0.00018 (< 0.05), KPSS p = 0.1 (> 0.05) → **정상. 차분 불필요** |
| 12, 17 | 요일별 분포 | **요일별 평균 대기가 평탄하다** — 월 18.2 / 화 19.0 / 수 20.2 / 목 18.2 / 금 20.0 / 토 20.4 / 일 21.2분. 최대–최소 3.0분. 건수는 평일 25~27만 vs 주말 9~10만으로 크게 갈린다 |

**해석 — 왜 이 결과가 모델 설계에 쓰이는가**

수요는 요일에 따라 2.5배 이상 흔들리는데(주말 급감) **대기시간은 요일에 거의 반응하지
않는다.** 공급이 수요를 따라 조정되고 있다는 뜻이라, 요일을 대기 모델의 주 설명변수로
둘 근거가 약하다. 현재 코드가 요일을 **이동시간 테이블의 평일/주말 2분할로만** 쓰고
대기 지표에는 요일 축을 두지 않는 것이 이 결과와 정합적이다.

**한계**

- 노트북의 `대기분` 은 **배차 − 예정**(매칭 대기)이고, 이 저장소의 검증 기준 39.3분은
  **승차 − 접수**(총 대기)다. **정의가 다르므로 18~21분과 39.3분을 직접 비교하면 안 된다.**
  대응되는 값은 `metrics` 의 `wait_match_mean`(서울 합산 20.82분)이다.
- 노트북은 **즉시콜·서울 필터를 걸지 않은 원본 전수**를 쓴다고 적혀 있다. 그렇다면 시뮬
  입력 모수 1,527,213건과 모집단이 다르다(위 ⚠ 참조).
- 노트북 안의 입력 경로가 작성자 로컬 경로라 **그대로는 실행되지 않는다.** 출력이 셀에
  저장돼 있어 결과 확인은 가능하지만 재실행에는 경로 수정이 필요하다.
- 시계열 분해는 `src/*` 에 반영돼 있지 않다. 현재 코드가 남기는 수요 분해는
  `metrics.demand_matrix()` 의 동 × 시간대(4구간) × 평일/주말 3,414행뿐이며
  **월·주 단위 변동은 접혀 있다.**

## 4. 코드와 어긋난 지점

전달받은 설명과 코드·파일 실물이 어긋난 곳이다. **모두 코드·파일 쪽을 따랐다.**

| 항목 | 전달받은 설명 | 코드·파일 실물 | 채택 |
|---|---|---|---|
| 공영주차장 좌표 유효 건수 | 117 / 850 | `공영주차장_목록.csv` **2,189행 중 좌표 유효 1,456**(전부 시영), 무효 733(전부 구영). **117** 은 `시영주차장_목록.csv` 122행 중 공영 파일에 `PKLT_CD` 로 존재하는 행수다. **850** 에 해당하는 값은 어느 파일에서도 나오지 않는다 | 1,456 / 2,189 |
| 공영·시영 주차장 목록의 코드 사용 | 아직 코드가 읽지 않음 | `공영주차장_목록.csv` 는 `load.load_candidates()` 가 **읽는다**(호출처는 `load.py.__main__` 진단 출력과 테스트). 다만 결과가 지표·시뮬로 흘러가지 않는다. `시영주차장_목록.csv` 는 정말로 아무 모듈도 읽지 않는다 | 둘 다 "후보지 선별용, 미연결"로 기록 |
| `동별_거점용량_접근성.csv` 생성 | `step4_distance.py` 산출물(`load_undersupplied` docstring) | step4 가 실제로 쓰는 파일은 `동별_거점거리.csv` 이고 컬럼이 다르다(`3km내차고지수` 는 있으나 `3km내차량대수`·`최근접차고지용량`·`공급수준` 은 없다) | 생성 코드가 없다고 기록. `metrics.dong_supply()` 는 차고지 원본에서 직접 계산하므로 이 파일에 의존하지 않는다 |
| 동 경계 GeoJSON 의 현재 용도 | 대시보드 지도 (구현 예정) | 코드 일치 — `load.load_dong(with_boundary=True)` 에 읽는 분기가 있으나 호출하는 곳이 없다. 테스트도 `load_dong()`(중심점 분기)만 부른다 | "구현 예정"으로 기록 |
