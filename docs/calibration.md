# 캘리브레이션 근거

관문 C 타깃의 산출 근거, 콜 데이터 필터 정의, 알려진 데이터 한계를 모아둔 문서.
요약 표는 [README](../README.md#검증-기준-관문-c-캘리브레이션-타깃) 에 있다.

## 콜 데이터 전처리 (load.py)

원본 173만 행 → 즉시콜·서울 필터 후 **152.7만 건**(원본의 88.3%). 필터를 거친 실측 대기시간이
아래 관문 C 타깃과 일치하는 것으로 필터 정의를 검증했다(`pytest -m slow`).

- **즉시콜** `|예정 − 접수| ≤ 2분`
- **서울** 출발구가 서울 25구. 원본에 경기·인천 건이 섞여 있다.
- **동 좌표 매칭** — 콜 원본은 `고덕제1동`, 경계 파일은 `고덕1동` 표기라 그냥 두면
  441개 조합 중 219개가 어긋난다. `analysis/step3_match.py` 와 같은 3단계로 맞춘다:

  | 단계 | 방식 | 건수 |
  |---|---|---|
  | exact | 숫자 앞 '제'·공백·구두점 제거 후 일치 | 1,472,892 |
  | approx | 분동/합동은 같은 기본명 그룹 중심점 평균 | 44,105 |
  | manual | 행정구역 개편으로 개명된 동(용신동 등) | 10,216 |

- 첫 실행은 1~2분, 이후 `cache/*.parquet` 재사용(0.2초). 원본이 바뀌면 자동 무효화.

### 알려진 데이터 한계

- **후보지 풀이 시영 전용** — `공영주차장_목록.csv` 2,189곳 중 좌표가 있는 건
  시영 1,456곳뿐이고, 자치구영 733곳은 LAT/LOT 가 전부 0 이다. 구영을 후보에
  넣으려면 `analysis/step1_geocode.py` 로 주소 지오코딩을 먼저 돌려야 한다.
- **목적동 좌표 결측 7.3%** — 대부분 서울 밖 목적지다. 서울 내 미매칭은 극소수이며
  전부 인천 중구 동(영종동·율목동·신흥동)이 서울 중구로 잘못 적재된 건이다.
- **재현성 공백** — 즉시콜·서울 필터 후 132만을 만든 원본 집계 스크립트는 저장소에
  없고 산출물 CSV(`서울즉시콜_*.csv`)만 존재한다. `analysis/step3_match.py` 가 그
  파일을 읽어 쓰지만 생성하는 코드는 step1~6 어디에도 없다. `load.py` 가 이 역할을
  대체하며, 취소 콜까지 보존해 152.7만으로 확장했다. 동별 건수는 원본과 완전히
  일치하고(공통 430개 동 차이 0), 동별 평균대기도 최대 0.05분 차이(원본 반올림)다.

## 이동시간 (travel_time.py)

`calltaxi_2025_병합.csv` 의 승차→하차 실측에서 뽑는다. 원본 148.8만 → 매칭 Y 147.8만
→ 출발·목적 모두 서울 136.3만 → 운행 1~120분·거리>0 135.4만 → 속도 2~60km/h **135.3만**.
중앙 **19.6분 / 5.03km / 15.7km/h** 로 참고 실측(20분 / 5.5km / 16km/h)과 맞는다.

조회는 3단 폴백이다. 커버율은 표 산출에 쓴 데이터 기준(in-sample):

| 순위 | 방식 | 커버 | 실측 대비 절대중앙오차 |
|---|---|---|---|
| 1 실측 OD | (출발동, 목적동, 시간대, 평일/주말) 중앙값, 10건 이상 | 79.9% | 2.1분 |
| 2 속도 테이블 | 직선거리 × 1.36 ÷ (거리대·시간대·요일 중앙속도) | 19.8% | 5.0분 |
| 3 직선 근사 | 위 셀이 비면 시간대·요일 평균속도로 같은 계산 | 0.0% | — |
| 동 내부 | 출발동 == 목적동 — 실측 동일-동 중앙값(5~7분) | 0.3% | 2.1분 |
| 좌표없음 | 중심점을 못 찾는 동 — 시간대 운행시간 중앙값 | 0.02% | 57.5분 |

좌표없음 322건은 전부 서울 중구로 잘못 적재된 인천 중구 동(영종동 등)이라
실제로는 서울 밖 장거리인데 서울 중앙값 20분으로 답한다. 오차가 크지만
0.02%라 지표에 영향이 없다.

거리대별 중앙속도(km/h)는 `~2km` 12.1 / `2-5km` 15.0 / `5-10km` 17.6 /
`10-20km` 22.4 / `20km+` 30.9 로, 멀수록 간선·고속 이용이 늘어 빨라진다.
50칸(거리대 5 × 시간대 5 × 요일 2)이 전부 357건 이상으로 차 있다.

전체 절대중앙오차 2.4분, 반환값은 항상 1~120분이다. 전 동쌍(425² = 18만 조합) ×
시간대를 전수 조회해도 결측·0·음수가 없다.

**우회계수 1.36 은 실측과 맞는다.** 30건 이상 OD쌍 8,069개에서
`중앙 승차거리 ÷ 중심점 직선거리` = 중앙 1.334 / 평균 1.388.

### 알려진 한계

- **1순위 커버가 79.9%인 이유.** OD쌍만으로 끊으면 89.9%지만(참고 수치 88%가 이 값이다)
  시간대·요일까지 나누면 셀이 얇아져 20%가 2순위로 내려간다. 요일만 추가하면 86.7%,
  시간대만 추가하면 83.1%. 피크 혼잡 반영과 맞바꾼 것이고, 2순위 오차가 5.0분이라
  감수할 만하다.
- **거리대는 5구간이다** — ~2km / 2~5km / 5~10km / 10~20km / 20km+. 멀수록 간선·고속 이용이 늘어 속도가 12.1 → 30.9km/h로 단조 증가한다. 거리대를 더 쪼갤 때는 검증 출력의 셀별 건수를 확인할 것 — MIN_SPEED_TRIPS(30) 미만 셀은 표에서 빠져 3순위로 흘러간다.
- **동명만으로 조회한다.** `get_travel_time(출발동, 목적동, hour, is_weekend)` 시그니처가
  구를 받지 않아 `신사동`(강남·관악)처럼 겹치는 동명은 좌표를 평균하고 실측도 한 셀에
  섞인다. 425개 중 1개다.
- **시간대 구분이 load.py 와 다르다.** load 는 대기 집계용 4구간(심야/아침/낮/저녁),
  travel_time 은 혼잡 반영용 5구간(심야/오전피크/낮/오후피크/저녁)이다. 섞어 쓰지 말 것.

## 검증 기준 (관문 C 캘리브레이션 타깃)

현행 배치로 돌렸을 때 실측값 재현 여부로 판정한다.
**지표마다 분모가 다르니 대조할 때 주의할 것.**

| 지표 | 실측 목표 | 분모 |
|---|---|---|
| 평균 대기 | 39.3분 | 승차 완료 **1,323,620** |
| 중앙값 | 30.8분 | 〃 |
| p90 | 77.2분 | 〃 |
| 장기대기(60분 초과) | 17.9% | 〃 |
| 취소율 | **13.3%** ※ | 시뮬 입력 모수 **1,527,213** |
| 지역 지니(동) | 0.095 † | 100건 이상 동 **430개** |

※ **취소율 정정 (구 14.2%).** 기존 14.2%는 필터 이전 원본 전체(1,729,476)를 분모로
쓴 값이라 다른 지표와 모수가 어긋나 있었다. 시뮬 입력 모수(즉시콜+서울, 1,527,213)와
분모를 통일해 **13.3%**로 정정한다. 대기시간 4개 지표는 별도 조치 없이 승차 완료
1,323,620건 기준으로 산출된다 — 취소 건은 `wait_min`이 NaN 이라 통계에서 자동 제외된다.
같은 이유로 시뮬 입력을 152.7만으로 두어도 평균 39.3분은 그대로 재현된다.

† **지니는 동 균등가중이 정본이다.** 형평을 '동 간 격차'로 정의하므로 각 동을 한 표로
센다. 콜수로 가중하면 콜이 많은 동이 지표를 지배해 정작 소외된 동의 격차가 묻힌다.
원본 산출물로 역산한 타깃 0.095 도 균등가중 값(0.0947)이라 정의와 실측이 일치한다.
`metrics.dong_gini()` 는 균등가중이 기본이고, `weighted=True` 로 콜수 가중도 뽑을 수
있게 남겨뒀으나 참고용이며 관문 C 채점에는 쓰지 않는다.
